# Архитектура

Как устроен проект и почему так. Описывает то, что есть в репозитории на
18 октября 2026, без планов и пожеланий.

## Что это

Телеграм-бот и Mini App к нему: человек присылает фото еды, модель определяет
блюда, бот считает КБЖУ, ведёт дневник и присылает советы. Монорепозиторий pnpm
из двух приложений и одной схемы базы.

```
apps/bot-api     Fastify + grammY + Prisma. Бот, API для Mini App, задания по расписанию.
apps/webapp      React + Vite. Mini App внутри Telegram.
api/index.ts     Точка входа для Vercel: динамический импорт собранного сервера.
```

Один и тот же процесс обслуживает и бота, и API: на Vercel это одна
serverless-функция, вебхук Telegram приходит на `/api/tg-webhook`.

## Как идёт запрос

**Фото еды.** Telegram → вебхук → `bot/handlers/food.ts` → проверка лимитов и
блокировки → скачивание файла (`services/tgfiles.ts`) → vision-модель
(`ai/food.ts`) → запись приёма (`services/meals.ts`) → сверка с режимом питания
(`ai/dietCheck.ts`) → карточка (`bot/mealCard.ts` + `bot/cards.ts`).

**Mini App.** Telegram отдаёт `initData` → `POST /api/auth/telegram` проверяет
подпись (`auth/initData.ts`) и выдаёт JWT на 12 часов → экраны ходят в
`/api/*` с этим токеном. Фото отдаются отдельной короткой подписью
(`auth/photoToken.ts`), а не сессионным токеном: ссылка на картинку попадает в
логи и кэш, и полный доступ там держать нельзя.

**Расписание.** Vercel Cron дёргает `/api/cron/hourly` и `/api/cron/daily` с
секретом в заголовке. Внутри — тики из `cron/`: советы, итоги челленджей,
вечерние напоминания, месячные отчёты, истечение подписок.

## Границы слоёв

| Слой | Папка | Правило |
|---|---|---|
| Чистые правила | `src/*.ts` (`challenges.ts`, `diets.ts`, `feed.ts`) | Без базы и сети. Покрываются юнит-тестами. |
| Сервисы | `src/services/` | Работа с базой. Не знают про Telegram и HTTP. |
| Модель | `src/ai/`, `src/prompts/` | Вызовы провайдеров и промпты. Возвращают разобранные данные или null. |
| Бот | `src/bot/` | Тексты, кнопки, обработчики апдейтов. |
| HTTP | `src/api/` | Маршруты, проверка прав, сериализация. |
| Расписание | `src/cron/` | Тики с бюджетом времени; правила выбора дня — в `cron/schedule.ts`. |

Правило, которое держит всё это: решение, которое можно проверить без базы,
живёт в чистом модуле. Поэтому выполнимость челленджа, границы недели,
порядок ленты и выбор дня для рассылки лежат отдельно от кода, который их
применяет.

## Бот по частям

`bot/bot.ts` только собирает бота из композеров grammY и задаёт порядок:

```
payments → account → recipes → challenges → food
```

Порядок важен: часть про еду ловит любое фото и любой текст, поэтому идёт
последней, иначе перехватит команды остальных.

| Модуль | За что отвечает |
|---|---|
| `handlers/account.ts` | `/start` (включая вход по ссылке-приглашению), `/day`, `/settings`, `/delete`, вечернее напоминание |
| `handlers/food.ts` | Фото, текст, голос, уточнения, режим «можно?», кнопки под карточкой |
| `handlers/recipes.ts` | «Мои блюда»: запись привычной еды без вызовов модели |
| `handlers/challenges.ts` | Шаблоны, проверка выполнимости, старт и выход |
| `mealCard.ts`, `cards.ts`, `keyboards.ts`, `helpers.ts` | Сборка карточек, кнопки и общие тексты |

## База

PostgreSQL, Prisma, 15 моделей, 10 миграций. На Vercel соединение идёт через
пулер Supabase (порт 6543, `pgbouncer=true`), миграции — через прямое
соединение (`DIRECT_URL`, порт 5432).

Особенности, которые стоит знать до первой правки схемы:

- **Миграции накатываются в сборке**, но только при `VERCEL_ENV=production`.
  Preview-сборки веток базу не трогают: переменные окружения в проекте общие,
  и раньше две сборки одновременно боролись за блокировку Prisma.
- **Миграции пишутся идемпотентно** (`IF NOT EXISTS`, `DO $$ … $$` для
  ограничений): часть из них исторически накатывалась руками через панель.
- **RLS включён на всех таблицах, политик нет.** Приложение ходит владельцем
  таблиц, владельца RLS не ограничивает, остальным ролям без политик не
  достаётся ничего. Таблицы, создаваемые в рантайме (`ProcessedUpdate`,
  `RecognitionLock`, `BenchImage`), включают RLS сами через `db.ts → enableRls`.
- **Счётчики ленты денормализованы** (`Meal.likeCount`, `voteCount`): лента
  читается на каждом свайпе, а голосуют реже.

## Что защищает от параллельности

Serverless-инстансы не делят память, поэтому всё, что должно быть общим, лежит
в базе:

- дневной лимит распознаваний — один SQL-запрос `INSERT … ON CONFLICT DO UPDATE
  … WHERE photoCount < limit RETURNING` (`services/limits.ts`);
- «одно распознавание на человека за раз» — `services/locks.ts`;
- дубликаты апдейтов Telegram — таблица `ProcessedUpdate`;
- один голос на пару человек-блюдо — первичный ключ `FeedVote`.

В памяти процесса остаётся только анти-спам `bot/queue.ts` (10 запросов в
минуту на пользователя) — он не критичен и переживает перезапуск без последствий.

## Незаконченное

**Лента еды («еда-тиндер»).** Схема и сервис готовы и покрыты тестами
(`services/feed.ts`, `feed.ts`), но ни один маршрут API и ни один экран их не
вызывает. Это заготовка, а не работающая функция. Публикация требует явного
действия: ни один существующий приём пищи не стал публичным.

**Оплата.** Код Telegram Stars на месте, но покупки выключены на сервере.
Выданные Pro-доступы продолжают работать.

**Стенд сравнения моделей** (`api/bench.ts`) открыт без пароля; единственная
защита — потолок расходов в день (`features.ts`).

## Mini App

Девять экранов, общие компоненты в `components/`, чистая логика в `lib/`.
Данные вкладок подгружаются заранее (`prefetch.ts`), иначе каждая вкладка
встречала человека спиннером. Ответы на устаревшие запросы отбрасываются общим
правилом `lib/latestRequest.ts` — человек быстро переключает выбор, а ответы
приходят в порядке сервера, не в порядке нажатий.
