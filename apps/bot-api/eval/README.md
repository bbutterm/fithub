# Инструменты eval

Прогон моделей распознавания еды по размеченному набору: одинаковые условия,
метрики считает код, решение принимаете вы.

Команды запускаются из корня репозитория:

```bash
pnpm --filter bot-api eval <команда>
```

## Порядок работы

| Шаг | Команда | Что делает |
|---|---|---|
| 1 | `eval validate` | Проверяет таблицу эталона и фото до того, как потрачены деньги |
| 2 | `eval prepare` | Приводит все фото к одному размеру и качеству |
| 3 | `eval run` | Прогон, перезапускаемый: повторный запуск не оплачивает сделанное |
| 4 | `eval label` | Файл для слепой разметки названий блюд |
| 5 | `eval score` | Метрики, отсев по порогам, отчёт и промахи с фотографиями |

Пороги, список моделей и число прогонов — в `eval/config.json`. Ключ берётся
из `VISION_API_KEY` (или `OPENROUTER_API_KEY`); база данных и остальные
переменные бота не нужны.

## 1. Что считается победой

Заполните `config.json` до начала работы:

```json
"thresholds": {
  "kcalErrorPctMean": 20,      // средняя ошибка по калориям
  "costPerPhotoUsd": 0.004,    // потолок цены за фото
  "latencySecP95": 10,         // допустимое время ответа
  "failureRatePct": 5          // доля битых и пустых ответов
}
```

`baseline` — текущая модель бота: она идёт в сравнение как точка отсчёта.
Идентификаторы моделей сверяйте с живым каталогом OpenRouter, а не со статьями:
в статьях они устаревают за недели.

## 2. Набор данных

Фото кладите в `eval/dataset/photos/`, эталон — в `eval/dataset/labels.csv`
(образец рядом: `labels.example.csv`).

| Колонка | Что в ней |
|---|---|
| `file` | Имя файла фото |
| `dish` | Название блюда, как назвали бы вы |
| `grams` | Вес порции по кухонным весам |
| `kcal`, `protein`, `fat`, `carbs` | Эталон на эту порцию |
| `source` | Откуда КБЖУ: упаковка, таблица, расчёт |
| `tags` | Тип блюда через `;` |
| `holdout` | `yes` для отложенных фото |

Метки типов: `simple`, `mixed`, `hidden` (скрытые калории: масло, соус, сыр),
`small`, `large`, `lowlight`, `multi` (несколько блюд на тарелке).

`validate` ловит пропавшие файлы, дубли, нечисла, неизвестные метки и
расхождение калорий с Б/Ж/У больше чем на четверть — почти всегда это описка в
граммах или не та строка таблицы калорийности.

Фото и прогоны не попадают в репозиторий: это личные данные и мегабайты.
Таблица эталона версионируется — она и есть ценность набора.

## 3. Прогон

```bash
pnpm --filter bot-api eval run                      # все модели из конфига
pnpm --filter bot-api eval run --models a,b --runs 3
pnpm --filter bot-api eval run --holdout            # только отложенные фото
```

Одинаковые условия обеспечены тем, что промпт и схема разбора берутся прямо из
кода бота (`src/prompts/vision.ts`, `src/ai/foodSchema.ts`), температура
фиксирована, фото подготовлены одной командой.

Каждый вызов пишется строкой в `runs/<дата>/calls.jsonl`: сырой ответ целиком,
разобранные числа, время, токены, цена, вид сбоя. Битый JSON и отказы считаются
ошибкой модели. Сетевые сбои и 429 повторяются и учитываются отдельной
колонкой — это не вина модели.

Прогон прерывается без потерь: запустите ту же команду с `--out <папка>`, и
готовые тройки «модель-фото-повтор» будут пропущены. Вышла новая модель —
добавьте её в конфиг и повторите команду, старые вызовы не оплачиваются заново.

## 4. Разметка названий

```bash
pnpm --filter bot-api eval label
```

Создаёт `labeling.csv`, где строки перемешаны, а названия моделей скрыты.
Заполните колонку вердикта значениями `верно`, `близко` или `мимо`. Соответствие
строк моделям лежит в `labeling-key.json` — не открывайте его до конца разметки.

## 5. Метрики и решение

```bash
pnpm --filter bot-api eval score
```

Считается по каждой модели: ошибка по калориям (средняя, медиана, 90-я
перцентиль, в процентах и в калориях), знак ошибки (завышает или занижает),
ошибка веса порции отдельно от КБЖУ, ошибки по белкам, жирам и углеводам в
граммах, доля сбоев, разброс между прогонами, время ответа и цена за фото.
Плюс разбивка по типам блюд и проценты ручной разметки.

Отчёт пишется в `runs/<дата>/report.md`, числа — в `metrics.json`, а
`misses.html` открывает пять худших промахов каждой модели вместе с
фотографией и сырым ответом: причину промаха видно только глазами.

Перед выводом отчёт сам проверяет то, о чём легко забыть: **разница между
лидерами должна быть больше разброса между прогонами**. Если нет — это шум, и
нужен больший набор или больше повторов.

Последний шаг — прогнать победителя на отложенных фото и сравнить с основным
результатом. Расхождение означает, что набор подогнан под модель.

## Что эти инструменты не делают

Не решают за вас. Порог точности, цена и выбор модели — ваше решение; код
только считает и показывает, где модель промахивается. Названия блюд размечаете
вы: автоматическое сравнение строк здесь врёт в обе стороны.
